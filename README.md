# PDF Translation App

A full-stack web application that allows users to upload PDF files, translate them into
multiple languages using AI-powered translation (DeepL or Mock provider), and read the
translated text directly in the browser. Built as a course project with 90%+ of the code
generated by GitHub Copilot.

> **Course project** — developer acted as reviewer, prompt engineer, and decision-maker.
> Minimal manual code editing.

## Prompting Patterns

Patterns that consistently gave the best results, distilled from the full project workflow.

### 1. Architecture before implementation

Define the full project structure, conventions, and layer responsibilities in instruction
files **before** writing any code. Copilot generates much better code when the guardrails
already exist — every subsequent session inherits the same constraints automatically.

*Applied in:* Step 2 (project-structure instruction), Step 6 (facade rule escalation).

### 2. Feature doc → split → task → implement pipeline

The most effective end-to-end pattern:

1. Write a feature doc with user stories (`docs/features/<feature>.md`).
2. Run `split-feature` prompt → produces small, tagged `[UI]`/`[API]`/`[DB]` task files.
3. Consolidate if too many tasks (`"Can you combine some tasks into one?"`).
4. Run `implement-task` prompt per task → one context file, one focused output.

Each task is small enough to be implemented correctly in a single pass.

*Applied in:* Steps 3–10 across all features.

### 3. One task = one unit of work

The smallest independent task consistently had the highest first-attempt success rate.
Mixing layers (UI + API in one task) or scoping too broadly increased failure rate and
introduced architectural inconsistencies.

### 4. State the observable fact, not the fix

*"I see error X / I expect Y"* outperforms *"fix the bug"*. Copilot needs observable
evidence to reason from, not guesses. Paste the exact error message from the console —
no paraphrasing.

*Applied in:* Every bug fix in Steps 7–10 and Step 12.

### 5. Update prompts immediately on failure

When Copilot misses a rule once (e.g. skipping task completion markers, bypassing the
facade pattern), add that rule to the prompt or instruction file **before the next task**.
Repeating corrections conversationally does not propagate across sessions.

*Applied in:* Facade rule escalated to "Critical" after repeated violations; task-done
rule added permanently to `implement-task.prompt.md`.

### 6. Ask for suggestions when stuck

Asking *"suggest the next feature to implement"* when uncertain about priorities produces
well-reasoned, context-aware recommendations. Used successfully before the DeepL integration
step (Step 9) and before the unit testing phase (Step 12).

### 7. Consolidate before implementing

When a `split-feature` run produces too many tasks (e.g. 19 admin tasks), ask Copilot to
combine related ones before starting implementation. Fewer, slightly broader tasks reduce
context-switching overhead without losing coverage.

### 8. Right agent, right mode

Use `CSharpExpert` for all backend work and `angularExpert` for all frontend work. Switch
to **Ask** or **Plan** mode for exploratory conversations — staying in Agent mode during
exploration leads to unnecessary file edits and wasted context.

### 9. Package repetitive workflows into prompt files

Any multi-step git or automation workflow (branch → commit → push → PR) should be packaged
into a reusable `.prompt.md` file as early as possible. Doing this late forces manual
repetition for every release cycle.

*Applied in:* `pull-request.prompt.md`, `implement-unit-tests.prompt.md`.

## Insights

### What worked well

**Architecture-first prompting** — Defining the full project structure, constraints, and
conventions in instruction files before writing any code gave Copilot consistent, persistent
context across every session. The quality of generated code was noticeably higher when the
architectural guardrails were already in place.

**Task decomposition workflow** — The pipeline of `feature doc → split-feature prompt →
task files → implement-task prompt` was the single most effective pattern in the project.
Each task was small enough for Copilot to implement correctly in one pass, with minimal
back-and-forth.

**Iterative prompt refinement** — Treating prompt files as living documents (adding "delete
unused imports" mid-implementation, escalating the facade rule on repeated violations)
improved output quality incrementally. Each refinement carried forward to all future tasks
automatically.

**Specialized agents** — Giving `CSharpExpert` and `angularExpert` layer-specific context
(Clean Architecture rules for C#, facade + signals rules for Angular) produced more
architecturally consistent output than a generic agent would.

**Error-driven bug fixing** — Pasting the exact error message and stating the expected
behaviour ("I see X, I expect Y") was consistently effective. Most bugs were fixed in a
single attempt.

**Asking Copilot to suggest next steps** — When unsure what to tackle next, asking Copilot
for a recommendation produced well-reasoned, prioritised suggestions. Used successfully
before the DeepL integration step.

---

### What did not work

**Broad initialization prompts** — "Init the UI app" was too vague. Copilot generated
mocked implementations for all future features preemptively, requiring a full undo.
Lesson: scope every initialization prompt explicitly ("scaffold routing only",
"add layouts only", not "set up the whole frontend").

**Copilot skipping task completion markers** — Without an explicit rule, Copilot would
implement the code correctly but forget to update the task file status and add implementation
notes. Required a corrective prompt every time until the rule was added permanently to
`implement-task.prompt.md`.

**Facade pattern drift** — Even after adding the facade rule to the instruction file, some
generated components still skipped it. Required escalating the rule to "Critical" in both
the agent definition and the instructions file before it was consistently followed.

**No prompt for branch, push, and PR automation** — The git workflow (create branch,
commit, push, open PR) was never packaged into a reusable prompt file. Every release cycle
required manually kicking off the sequence, which broke the otherwise fully prompt-driven
flow. A dedicated `pull-request.prompt.md` should have been one of the very first prompts
created, not an afterthought.

**Context-switching between agents and modes** — On several occasions work was started in
the wrong agent — firing a C# task at `angularExpert`, or an Angular task at `CSharpExpert`
— only to notice mid-implementation that the output felt off. Similarly, forgetting to
switch from Agent mode to Ask or Plan when doing exploratory work led to unnecessary file
edits and wasted context. A quick mental checklist before each task (right agent? right
mode?) would have prevented these interruptions entirely.

### Step 12 — Unit testing (frontend)

**Context:** After the application was feature-complete, the focus shifted to test coverage.
Karma/Jasmine (the default Angular test runner) is officially deprecated, so the stack was
replaced with Jest + jest-preset-angular before writing any specs.

**Setup prompt:**
> Migrate the frontend test runner from Karma/Jasmine to Jest + jest-preset-angular.
> Remove all Karma packages from `package.json`, delete the Karma config, and add
> `jest.config.ts` and `setup-jest.ts` so that `npm test` works.

**Result:** Karma packages removed, `jest.config.ts` and `setup-jest.ts` added, `npm test`
running successfully with zero Karma dependencies.

**Prompt created:** `implement-unit-tests.prompt.md` — a dedicated prompt that drives the
`angularExpert` agent to write and run specs for a given set of task files. Key rules baked
into the prompt:

- Read the source file before writing assertions — never guess the public API.
- Mock services with `jest.fn()` plain objects; mock signal stores with `signal()` properties.
- Use `TestBed.overrideComponent` to replace a component's co-located facade (standard
  `TestBed.configureTestingModule` providers cannot override `providers` declared inside a
  component decorator).
- Run `npx tsc --noEmit` after writing specs; fix all TypeScript errors before running tests.
- On test failure: show the exact output and stop — never silently rewrite a spec to force
  a pass.

**How to use the prompt:**
1. Open `.github/prompts/implement-unit-tests.prompt.md` as the active prompt in Copilot.
2. Attach the task file(s) you want to test (e.g., `docs/features/unit-testing-tasks/06-[UI]-test-admin-facades-and-components.md`) as context.
3. Run with the `angularExpert` agent — the prompt selects it automatically.
4. The agent reads the task, reads the source file, writes the spec co-located with the
   source, runs `npm test -- --testPathPattern=<spec-file-name>`, and marks the task done.

**Bugs encountered and fixed via prompts:**

- *`takeUntilDestroyed` outside injection context* — facades using `takeUntilDestroyed`
  require `TestBed.configureTestingModule` even when no `fixture` is needed, because the
  Angular DI context must be active during construction.
- *Signal store mock shape mismatch* — initial mocks returned plain values instead of
  `signal()` wrappers, causing type errors in components that call signals as functions.
  Fixed by aligning mock shape to the real store's public API.
- *`navigator.clipboard` re-mocked in individual specs* — `setup-jest.ts` already defines
  a global clipboard mock; re-mocking it in a spec overrode it with an incompatible object.
  Rule added to the prompt: never re-mock `navigator.clipboard`.

**Outcome:** Full unit-test suite covering all facades, key components, and `FileSizePipe`.
`npm test` reports all specs passing.

# Part 2 — Project Reference

Technical documentation for running and understanding the application.

---

## Overview

| Layer | Technology |
|---|---|
| Frontend | Angular 20 (standalone components, signals, Angular Material) |
| Backend | ASP.NET Core 8, Clean Architecture (Domain / Application / Infrastructure / API) |
| Database | SQLite via EF Core 8 |
| Auth | JWT Bearer tokens, BCrypt password hashing |
| Translation | DeepL API or Mock provider (switchable at runtime via admin panel) |
| PDF Extraction | PdfPig (MIT license, no native dependencies) |

### Pages & Layouts

| Layout | Pages |
|---|---|
| `AuthLayout` | Login, Register |
| `MainLayout` | Upload, My Translations, Translation Detail |
| `AdminLayout` | Admin Settings, Admin Languages |

### Key Features

- Upload a PDF and queue a background translation job via `Channel<Guid>`
- Real-time status polling (3 s on detail page / 5 s on list page) using Angular signals + RxJS intervals
- One document can be translated into many languages simultaneously — results stored and displayed per language tab
- SHA-256 duplicate detection — re-uploading the same file reuses the existing document record
- Pluggable translation provider: swap Mock ↔ DeepL without restart or code change
- Admin panel: manage supported languages and translation provider/API key settings

## How to Run

### Backend

```bash
cd backend
dotnet restore
dotnet run --project TranslationApp.API
```

API runs at `http://localhost:5000`. Swagger UI at `/swagger`.
SQLite database (`app.db`) is created and migrated automatically on first run.
Default seed admin credentials are in `TranslationApp.API/appsettings.Development.json`.

### Frontend

```bash
cd frontend
npm install
ng serve
```

App runs at `http://localhost:4200`. API requests proxied via `proxy.conf.json`.

### Admin Access

A default admin account is seeded automatically on first run. Use these credentials to log in:

| Field | Value |
|---|---|
| Email | `admin@translationapp.dev` |
| Password | `Admin123!` |

After logging in, the **Admin** layout becomes available with two pages:

- `/admin/settings` — manage the active translation provider and API key
- `/admin/languages` — add languages or toggle them active/inactive

### Switching to DeepL

By default the app uses the **Mock** provider (returns placeholder text instantly, no API
key required). To enable real translation:

1. Log in as admin and navigate to **Admin → Settings**.
2. Change the **Translation Provider** dropdown from `Mock` to `DeepL`.
3. Enter a valid DeepL API key in the **API Key** field. A free-tier key is already
   available for local development:
   ```
   30d05b64-85b3-47d8-926e-7e1da9155a26:fx
   ```
4. Check the **Use Free DeepL API** checkbox — free-tier keys end in `:fx` and require
   this flag so the provider targets the correct API endpoint.
5. Click **Save** — the change takes effect immediately for all subsequent jobs without
   restarting the server.

A working DeepL Free-tier API key is already pre-configured in
`TranslationApp.API/appsettings.Development.json` for local development.

> **Note:** The DeepL Free tier allows up to **500,000 characters/month**. If translation
> jobs start returning 403 or quota errors, the monthly limit has been reached — switch
> back to the **Mock** provider until the quota resets.
